# Ежедневная сводка support-отдела

Интерактивное демо для тестового задания по AI-автоматизации: сопоставление статусов CRM и сообщений, приоритеты, проверки и следующие действия. В приложении используются учебные случаи; реальные CRM и чаты не подключены.

Демо GitHub Pages: https://dm-morozov.github.io/russmarket-support-digest/ (доступность подтверждается итоговой проверкой публикации).

Основной ответ: [сводка четырёх случаев](docs/digest.md), [первый запуск в 6 предложениях](docs/launch.md), [архитектура](docs/architecture.md), [показ за 60 секунд](docs/demo.md).

## Как попробовать

На странице выберите исходный пример и нажмите «Сформировать сводку». Затем переключите сценарий на полученные подтверждения или противоречия и обработайте снова. JSON можно редактировать: новые ID, статусы, даты и подтверждения действительно пересчитывают результат. Старый результат сбрасывается сразу после изменения ввода.

Публичное демо — статический сайт GitHub Pages. JavaScript выполняет правила в браузере, а не показывает заранее сохранённую сводку. Ввод не отправляется на сервер, не записывается в localStorage/cookies и теряется при обновлении страницы. Единственный запрос приложения после загрузки кода — чтение готовых учебных примеров с того же сайта. Не вводите реальные персональные данные: эта демонстрация не предназначена для рабочего использования.

## Локальный запуск

Для Python CLI и локального просмотра нужен Python 3.10+ без сторонних библиотек:

```bash
python digest.py examples/monday.json
python digest.py examples/monday.json --format json
python demo.py
```

После последней команды откройте http://127.0.0.1:8765/. Остановка — Ctrl+C. Предпросмотр собирает и обслуживает тот же статический каталог, который публикуется на Pages; локальный сервер не является backend обработки данных. Для публичного демо сервер, Gunicorn, SSH-ключи и отдельный домен не нужны.

## Способ обработки

Использован разрешённый заданием вариант — скрипт с описанными правилами. Python CLI служит основной проверяемой реализацией, а небольшой JavaScript-обработчик делает тот же расчёт на статическом сайте. Между ними есть явное дублирование алгоритма; CI сравнивает полные результаты на автоматически получаемой из Python матрице из более чем 300 входов. Это проверка согласованности на покрытой выборке, а не доказательство эквивалентности для любого возможного входа.

1. Источники остаются раздельными: записи CRM и заявления из чатов не смешиваются. ID используются для связи и отображения, а не для выбора бизнес-правила.
2. Отправка фотографий в личку не подтверждает получение и комплектность документов; пересказ сотрудника не заменяет прямое подтверждение руководителя.
3. Незавершённая доставка при наступившем сроке или ETA позже срока получает приоритет 1. Известный срок сохраняет срочность и при неизвестном статусе.
4. Увольнение сегодня без подтверждения руководителя — приоритет 2; документы перед завтрашним выходом — приоритет 3, запросить сегодня. Состояние «неизвестно» не выдаётся ни за положительное, ни за отрицательное подтверждение.
5. Подтверждённая в CRM приёмка — плановая сверка. Статус принятия без времени подтверждения, отсутствующие существенные данные и отмеченные противоречия требуют ручной проверки.

Поле `chat.conflicts_with_crm` выставляет сотрудник при подготовке данных: приложение не понимает произвольный текст и не находит смысловые противоречия автоматически. Текст чата не исполняется и не может самостоятельно изменить подтверждение. Порядок внутри равного приоритета определяется ID для стабильности вывода; фактическую очередь согласует support-отдел.

## Входные данные и допущения

JSON содержит `as_of`, массив `cases` и необязательный текст `context`. Каждый случай включает непустые `id`/`kind`, объекты `crm`/`chat` и описание `evidence`. Неизвестное подтверждение задаётся `null`, отсутствие подтверждения — `false`. Для типа доставки используются `status`, `due_at`, `accepted_at` и необязательный `chat.eta_at`; подтверждения оформления/увольнения задаются отдельными boolean-полями.

Календарная дата: `YYYY-MM-DD`. Время: `YYYY-MM-DDTHH:MM:SS[.ffffff]` с UTC-смещением `±HH:MM` или `Z`. Сравнения поддерживают микросекунды; календарные дни оформления/увольнения относятся к часовому поясу `as_of`. Неверные типы, даты и дубликаты ID дают ошибку вместо частичной сводки. Лимит — 100 случаев; редактор принимает до 128 КиБ JSON.

В задании дано «понедельник, 10:00» без даты и часового пояса. Дата 19.10.2026 и UTC+03:00 выбраны только для воспроизводимого примера и отмечены в сводке. Для П-08 «не раньше 13:00» — нижняя граница, а не гарантия прибытия. Для П-09 проверка количества известна только из переписки, отдельного подтверждения количества в CRM нет.

## Проверки и публикация

```bash
python -m unittest -v
python scripts/generate_parity.py
node --test tests/engine.test.mjs
python scripts/build_pages.py
```

Node.js 20+ нужен только для parity-тестов, npm install не требуется. Проверяются бизнес-правила Python, сохранённая UTF-8-сводка, даты/часовые пояса/микросекунды, неизвестные и конфликтующие данные, ошибки, произвольные ID, отсутствие изменения источников и состав статического артефакта. JavaScript сравнивается с результатами Python на всех трёх демонстрационных сценариях и расширенной матрице граничных входов.

GitHub Actions выполняет тесты → сборку `dist/` → публикацию Pages только из main. Разрешения публикации ограничены `pages: write` и `id-token: write`, чтение кода — `contents: read`; пользовательские deploy-секреты не нужны. Сборка переносит только разрешённые файлы; PDF, переписка и служебные материалы в исходники и артефакт не входят. Подробности фактической проверки: [verification.md](docs/verification.md).

Не проверены реальная экономия времени, полнота/свежесть рабочей выгрузки, корректность нормализации свободных сообщений и интеграция с реальными системами. Это темы первого пилота с support-отделом, а не выполненные возможности демо. Приложение не оформляет/увольняет сотрудников, не проводит операции с картами и не отправляет сообщения.

## Использование ИИ

Решение подготовлено ИИ-помощником по поручению Дмитрия Морозова. Помощник реализовал код, документацию и выполнил проверки. Само приложение использует детерминированные правила; LLM и API моделей не подключены. Это раскрытие процесса подготовки, а не заявление о ручной реализации или проверке Дмитрием.
